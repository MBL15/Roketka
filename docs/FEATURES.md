Файл отвечает на два вопроса: что именно в прототипе работает и чего в нём
осознанно нет. Второе не менее важно первого — граница MVP должна быть
проведена явно, а не обнаружена при проверке.

## Обязательные требования

### Экран выбора ставки

| | Требование | Как сделано |
|---|---|---|
| + | Четыре варианта ставки — фрагменты пазла | `PuzzleCard.tsx`: четыре разные фигуры через `clip-path`, вместе складываются в целое изображение |
| + | У каждого варианта своя стоимость и множитель бустера | Берутся из `GET /api/game/setup`, ни одно число не зашито в интерфейс |
| + | При недостатке баланса вариант недоступен и подписан «Не хватает бонусов» | Признак `affordable` считает сервер; карточка получает `disabled` и подпись |
| + | «Начать» активна только после выбора доступного варианта | Кнопка заблокирована, пока в состоянии нет выбранного доступного варианта |
| + | «Начать» проигрывает анимацию активации и списывает баллы | Анимация сборки пазла + звук; списание — транзакция `POST /api/rounds` |
| + | Общая история раундов **всех** игроков с коэффициентами | `HistoryFeed.tsx` + `GET /api/game/history`; обновляется по событию `history.updated` |
| + | Доступ к правилам до подтверждения ставки | `RulesModal.tsx`, кнопка «Правила» на экране ставки; текст собирается из активной конфигурации |
| + | Отображение количества уровней | `LevelLadder.tsx` показывает все уровни темы с их границами |
| + | Понятная стоимость ставки и условия активации бустера | Стоимость на карточке, условие активации — в правилах и в подсказке на лестнице уровней |

### Полёт

| | Требование | Как сделано |
|---|---|---|
| + | Точка краха генерируется на сервере до начала полёта | `RoundService.start()` → `CrashMath.sampleCrashPoint()`; в ответ уходит только хеш зерна |
| + | Кнопка «Забрать» видна, но выключена до прохождения первого уровня | Проверяется и в интерфейсе, и на сервере (`409 round_rejected`) |
| + | При нажатии коэффициент фиксируется, выплата = ставка × коэффициент | Коэффициент берётся из серверного времени обработки запроса, не из тела |
| + | После фиксации шар продолжает лететь до краха | Статус `CASHED_OUT`, раунд становится терминальным (`WON`) только при крахе |
| + | Сообщение «Могли бы забрать больше» | На экране результата, когда точка краха выше зафиксированного коэффициента |
| + | Стиль коэффициента зависит от прогресса | 0–1 чёрный, 1–2 жёлтый, 2–3 жёлтый со свечением, 3+ жёлтый со свечением и крупнее |
| + | Мини-онбординг «Нажми "Забрать" до того, как шар лопнет» | Анимированная стрелка, показ `session.onboardingHintSeconds` (по умолчанию 4 с), затем плавно исчезает; только в первом раунде игрока |
| + | За прохождение уровня начисляется `points_per_line` с эффектом «+X» и звуком | Событие `round.level` → всплывающее «+10» и звук; начисление считает сервер |
| + | Бустер ждёт на выбранном сервером уровне по `line_N_loot_prob` | `CrashMath.pickBoostLevel()` по нормированным весам |
| + | Бустер умножает коэффициент на `multiplier_tier_N_value` и даёт очки | Событие `round.boost`; вспышка на канвасе и звук |
| + | Бустер не активируется после фиксации выигрыша | Проверка в игровом цикле: после `CASHED_OUT` бустер пропускается |

### Экран результата

| | Требование | Как сделано |
|---|---|---|
| + | Открывается только после краха шара | До краха `GET /api/rounds/{id}/result` отвечает `202 round_in_flight` — правило держит API, а не только интерфейс |
| + | При выигрыше: сумма, коэффициент, потенциальный максимум | `payout`, `cashoutMultiplier`, `potentialMaxMultiplier` |
| + | При проигрыше: сообщение и коэффициент краха | Отдельное оформление экрана, без потенциального максимума |
| + | Игровые очки за раунд начисляются в обоих случаях | Блок `points` в ответе ненулевой и при проигрыше — очки за пройденные уровни |
| + | Дополнительная награда встроена в прогрессию | Коллекция «Карта неба»: фрагмент за каждый раунд, за собранную коллекцию — очки и бонусные баллы. Не декоративная иконка: влияет на турнирный результат и на баланс |
| + | Награда объяснена в правилах | Отдельный раздел в `RulesModal.tsx`, текст берёт числа из конфигурации |
| + | «Играть снова» сохраняет выбранную тему | Возврат на экран ставки той же темы |
| + | «Повторить с той же ставкой» (необязательное) | Отдельная кнопка: сразу начинает раунд тем же вариантом, если хватает баланса |
| + | 10 секунд бездействия → экран выбора темы | Таймаут из `session.resultIdleTimeoutSeconds`, сбрасывается любым действием |

### Управление параметрами

| | Требование | Как сделано |
|---|---|---|
| + | Изменение параметров без правки кода | `config/game-config.yaml` с горячей перезагрузкой **и** веб-админка на `/#admin` |
| + | Все обязательные группы параметров | Базовые, математика, вероятности бустера по темам, значения множителей, правила очков — все присутствуют, см. [CONFIGURATION.md](CONFIGURATION.md) |
| + | Валидация значений | Один валидатор для файла и для админки; некорректная версия отклоняется, игра продолжает работать на предыдущей |
| + | Пояснения к параметрам | Комментарии в YAML сохраняются при записи из админки, плюс подсказки в самой админке |

Ключевое решение: админка пишет в тот же файл, который правят руками. Два
способа управления не могут разойтись, потому что источник правды один.

## Нефункциональные требования

| | Требование | Как выполнено |
|---|---|---|
| + | 60 FPS анимации | Клиент один раз получает `startedAtMillis` и `growthRate` и считает коэффициент сам той же формулой, что сервер. Сеть не участвует в отрисовке кадра |
| + | Без тяжёлых графических библиотек | Canvas 2D и CSS. Ни одной библиотеки анимации или UI-кита; в `package.json` только React, Vite и TypeScript |
| + | Адаптивность 320–1920 px | Вёрстка на `clamp()` и относительных единицах, канвас перестраивается по `ResizeObserver` с учётом `devicePixelRatio` |
| + | Генерация случайных чисел только на сервере | В коде клиента нет `Math.random()` для игровых величин; исходы приходят с сервера |
| + | Упрощённый provably fair с хешем | `SHA-256(serverSeed)` выдаётся до полёта, зерно раскрывается в результате, пересчёт — `GET /api/fairness/verify` |
| + | Режим разработки с фиксированным seed | `balloon.dev-seed` (переменная `DEV_SEED`) делает последовательность раундов воспроизводимой от запуска к запуску; параметр `seed` в симуляторе — то же для Monte-Carlo серии |
| ± | Chrome, Safari, Firefox | Проверено в Chrome и Firefox. В Safari не проверялось: под рукой не было устройства. Использованные API (Canvas 2D, WebSocket, Web Audio, `clip-path`, CSS-переменные) поддерживаются Safari 15+, поэтому ожидаем работоспособность, но заявить проверку не можем |

## Что сделано сверх постановки

Ни один из этих пунктов не был обязательным; каждый закрывает конкретный риск.

**Monte-Carlo симулятор экономики** (`POST /api/admin/simulate`, вкладка в
админке). Влияние `alpha`, `houseEdge` или `alphaShift` невозможно оценить по
одному раунду. Симулятор прогоняет десятки тысяч раундов по каждому варианту
ставки и показывает RTP, долю выигрышных раундов и вероятность дожить до
бустера. Принимает черновик конфигурации, поэтому последствия правки видны до
сохранения.

**Полный резервный канал на REST.** `GET /api/rounds/{id}/state` и
`GET /api/tournament/live` отдают те же данные, что WebSocket. Если сокет не
поднялся, интерфейс сам переходит на опрос с периодом 700 мс — игра
продолжается, в верхней строке меняется индикатор связи. Это проверяется
блокировкой WebSocket в инструментах разработчика.

**Снимок параметров в раунде.** Каждый раунд хранит `@Embeddable
RoundParameters` — значения, с которыми он был создан. Поэтому изменение
конфигурации не может повлиять на исход уже летящего раунда, а проверка
честности спустя месяц пересчитывает исход по историческим параметрам, а не по
текущим.

**Звук без бинарных файлов.** Все эффекты синтезируются через Web Audio API
(`AudioEngine.ts`). В репозитории нет ни одного аудиофайла: нет вопросов о
лицензиях на сэмплы и нет лишних сетевых запросов.

**Сохранение комментариев в YAML.** Админка записывает файл через собственный
сериализатор, который сохраняет структуру и пояснения. Без этого первое же
сохранение из UI уничтожило бы всю документацию внутри конфига и сделало бы
ручную правку неудобной.

**«Последняя рабочая конфигурация».** Опечатка в YAML не останавливает игру:
сервер продолжает работать на предыдущей корректной версии и показывает причину
отказа в `GET /api/admin/config/status` и в админке.

## Ограничения

### Продуктовые

Покупка лотерейных билетов **имитируется**: списываются бонусные баллы, растёт
счётчик билетов. Реальной интеграции с платёжной системой и с тиражами нет —
это выходит за рамки прототипа игровой механики.

Соперники в турнире — **боты**. Они набирают очки по случайному процессу
(`tournament.simulation`), чтобы рейтинг был живым на демонстрации с одним
игроком. Симуляцию можно выключить одним флагом в конфигурации, и тогда в
таблице останутся только реальные игроки. Боты помечены полем `bot: true` —
это видно и в API, и в интерфейсе.

Регистрация без подтверждения адреса и без восстановления пароля.

### Технические

**Отдельной роли администратора нет.** Для доступа к `/api/admin/*` достаточно
действующей игровой сессии. Для прототипа, который разворачивается на время
проверки, это осознанное упрощение, но для эксплуатации потребовалась бы
авторизация по роли. Способ уже подготовлен: `AuthContext` доезжает до каждого
метода админки, так что проверка добавляется в одном месте.

**Игровой цикл выполняется в одном экземпляре приложения.** Активные раунды
живут в памяти процесса (`ConcurrentHashMap`), поэтому две копии бэкенда за
балансировщиком нельзя запускать без доработки. Путь к горизонтальному
масштабированию описан в
[ARCHITECTURE.md](ARCHITECTURE.md#путь-к-горизонтальному-масштабированию): sticky
routing по `roundId` либо вынос состояния полёта в Redis. Для нагрузки
прототипа это не требуется: один поток тика обслуживает тысячи одновременных
полётов, потому что на каждом тике считается одна экспонента.

**Перезапуск сервера прерывает летящие раунды.** При старте незавершённые
раунды помечаются проигранными, ставка возвращается. Полноценное
восстановление полёта из базы не делали: раунд длится десятки секунд, и
возврат ставки — более честное поведение, чем попытка «догнать» время.

**Цепочка зёрен (commit-chain) не реализована.** Реализован упрощённый вариант,
которого требует постановка: одно зерно на раунд, хеш публикуется до полёта,
зерно раскрывается после. Полная схема, где зёрна образуют хеш-цепочку и
публикуются заранее на всю серию, доказывает ещё и отсутствие подбора зерна под
конкретного игрока. Это следующий шаг, а не то, что уже работает.

**H2 в файловом режиме по умолчанию.** Так прототип запускается одной командой
и не требует внешней СУБД. Профиль PostgreSQL есть и проверен
(`docker compose --profile postgres up`), схема одинакова — переключение
меняет только строку подключения.

**Схема базы создаётся Hibernate** (`ddl-auto: update`), миграций нет. Для
прототипа это удобно, для эксплуатации потребовался бы Liquibase или Flyway.

**Нет E2E-тестов интерфейса.** Backend покрыт модульными и интеграционными
тестами (57 тестов), включая проверку всех пяти обязательных сценариев на
уровне API. Интерфейс проверялся руками. Playwright не добавляли: на объёме
прототипа поддержка браузерных тестов стоила бы дороже, чем даёт.

**Safari не проверен** — см. таблицу нефункциональных требований выше.

**Локализация только русская.** Тексты лежат в компонентах, а не в файле
словаря; для второго языка потребовался бы их вынос.

## Что делали бы дальше

Список отражает приоритеты, а не полноту: первое важнее последнего.

1. **Роль администратора и журнал изменений конфигурации.** Сейчас видно, какая
   ревизия применена и кто её сохранил, но нет истории «что именно изменилось».
   Для игровой экономики это нужно.
2. **Цепочка зёрен вместо одиночного зерна** — усиливает проверяемость до
   промышленного уровня.
3. **Вынос состояния полёта в Redis** — снимает ограничение на один экземпляр
   и одновременно решает проблему перезапуска.
4. **A/B-тестирование параметров.** Конфигурация уже версионируется и
   применяется к новым раундам; следующий шаг — несколько одновременных
   вариантов с разбивкой по игрокам. Симулятор при этом становится инструментом
   предварительной оценки, а не единственным.
5. **Миграции схемы** (Flyway) перед первым реальным развёртыванием.
6. **Playwright-сценарии** на пять обязательных проверок — чтобы регрессии в
   интерфейсе ловились так же, как сейчас ловятся регрессии в математике.
