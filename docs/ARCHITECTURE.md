## 2. Разделение ответственности

Ключевой принцип: **клиент рисует, сервер решает.**

| Что | Где | Почему именно там |
| --- | --- | --- |
| Точка краха, позиция бустера | сервер, до старта полёта | исход нельзя изменить в процессе |
| Коэффициент на каждом кадре | клиент, локально | 60 FPS без сетевого трафика |
| Прохождение уровней, начисление очков | сервер | клиент может отстать или соврать |
| Расчёт выплаты | сервер | деньги считает только сервер |
| Анимация, звук, вспышки | клиент | не влияет на исход |

Клиент получает достаточно для отрисовки (время старта, темп роста, границы
уровней, снимок параметров) и недостаточно, чтобы узнать исход. Проверить это
легко: в ответе `POST /api/rounds` нет ни точки краха, ни уровня бустера — есть
только хеш зерна.

## 3. Слои backend

| Пакет | Ответственность | Ключевые классы |
| --- | --- | --- |
| `config` | загрузка, валидация, горячая перезагрузка, запись YAML | `GameConfigService`, `GameConfigValidator`, `GameConfigYamlWriter` |
| `domain` | JPA-сущности | `UserAccount`, `GameRound`, `RoundParameters`, `AuthSession` |
| `repo` | доступ к данным | Spring Data интерфейсы |
| `game` | чистая игровая механика | `CrashMath`, `FairnessService`, `ActiveRound`, `RoundEngine` |
| `service` | прикладные сценарии | `RoundService`, `TournamentService`, `RewardService`, `RtpSimulator` |
| `web` | HTTP-контракт | контроллеры, DTO, обработчик ошибок |
| `ws` | доставка событий | `GameSocketHandler` |

Зависимости направлены строго внутрь: `web` и `ws` знают про `service`,
`service` — про `game` и `repo`, `game` не знает ни про Spring MVC, ни про базу.
`CrashMath` — статические функции без состояния, поэтому её можно тестировать
сотнями тысяч прогонов без поднятия контекста.

## 4. Модель данных

```
users ──┬── rounds            (история и незавершённые раунды)
        ├── sessions          (токен + флаг показанного апсейла)
        └── collection_fragments
tournaments                   (период соревнования)
```

### users

| Поле | Смысл |
| --- | --- |
| `nickname` | уникальный, регистронезависимый |
| `password_hash` | PBKDF2WithHmacSHA256, 120 000 итераций, соль на пользователя |
| `bonus_balance` | ставочная валюта |
| `game_points` | турнирные очки (зеркало in-memory значения) |
| `lottery_tickets` | результат апсейла |
| `collection_level`, `rounds_played`, `onboarding_seen` | прогресс |
| `bot` | признак симулированного соперника |
| `entity_version` | `@Version` — оптимистичная блокировка баланса |

### rounds

Хранит всё, что нужно и для истории, и для проверки честности: ставку, бустер,
точку краха, коэффициент выхода, выплату, очки, зерно, хеш, nonce и полученную
награду.

Отдельного внимания заслуживает `@Embedded RoundParameters` — **снимок
параметров на момент старта раунда**: alpha, houseEdge, границы уровней, веса
бустера, правила начисления очков. Благодаря снимку:

- изменение конфигурации не может повлиять на уже летящий раунд;
- проверка честности спустя месяц пересчитает раунд по тем настройкам, с
  которыми он игрался, а не по текущим;
- восстановление после перезапуска не требует угадывать, какая конфигурация
  действовала.

Списки (границы уровней, веса) хранятся строкой с разделителем-запятой:
для снимка неизменяемых значений отдельная таблица дала бы только join.

## 5. Жизненный цикл раунда

```
POST /api/rounds
   ├─ проверить тему, отсутствие активного раунда, баланс
   ├─ списать ставку                                    ← транзакция
   ├─ serverSeed = SecureRandom(32), hash = SHA-256
   ├─ crash = CrashMath.sample(u(crash), alpha + alphaShift, ...)
   ├─ boostLevel = CrashMath.pickBoostLevel(u(loot), weights)
   ├─ сохранить GameRound со снимком параметров
   └─ RoundEngine.register(round)  → в ConcurrentHashMap

  ── тик раз в 1000/fps мс, один поток на все раунды ──
   ├─ base = exp(rate · t)
   ├─ пересечение уровня  → событие LevelCrossed  (+очки)
   ├─ достижение бустера  → событие BoostActivated (×множитель, +очки)
   └─ достижение краха    → передать в пул расчёта

POST /api/rounds/{id}/cashout
   ├─ ActiveRound.cashout() — проверки и расчёт в памяти
   ├─ зачислить выплату, обновить раунд                 ← транзакция
   └─ событие CashoutAccepted; шар продолжает лететь

  ── крах ──
   RoundSettlementService.settle()                      ← транзакция
   ├─ статус WON / LOST
   ├─ выдать фрагмент коллекции
   ├─ зафиксировать очки
   └─ события RoundCrashed, RoundSettled, HistoryUpdated, RatingUpdated

GET /api/rounds/{id}/result
   └─ 202, пока раунд не закрыт; затем полный результат с раскрытым зерном
```

Обратите внимание: экран результата открывается **только после краха**, даже
если выигрыш зафиксирован раньше. Это требование продукта, и оно же
естественно ложится на модель — до краха итог раунда просто не определён
полностью.

## 6. Движок раундов и производительность

`RoundEngine` — один планировщик на всё приложение:

- **один поток тиков** обходит `ConcurrentHashMap` активных раундов. Не поток
  на раунд: тысяча одновременных полётов — это тысяча вычислений `exp()` за
  тик, доли миллисекунды, а не тысяча контекстных переключений;
- **на горячем пути нет обращений к базе.** Тик работает только с памятью.
  Запись в БД происходит дважды за раунд: при фиксации выигрыша и при закрытии;
- **закрытие раунда вынесено в отдельный пул** из двух потоков, чтобы
  транзакция не задерживала тик остальных раундов;
- **частота тиков берётся из конфигурации** (`max(fps)` по темам) и
  перенастраивается на лету при изменении конфигурации.

Живой рейтинг держится в памяти (`TournamentService`) и сбрасывается в БД
пакетно раз в 5 секунд — очки меняются часто, а их потеря при аварии не
критична, поэтому запись на каждое начисление была бы неоправданной.

Транспорт не блокирует движок: движок публикует события через
`ApplicationEventPublisher`, а `GameSocketHandler` только кладёт кадр в очередь
клиента и возвращает управление. Тики и обновления рейтинга **склеиваются**:
если клиент не успевает читать, в слоте остаётся только последний кадр —
медленное соединение не отращивает очередь.

### Что нужно для горизонтального масштабирования

Сегодня узел один. Переход на несколько:

1. вынести активные раунды в Redis либо закрепить раунд за узлом по
   `roundId` (consistent hashing) — механика уже не зависит от порядка тиков;
2. заменить `ApplicationEventPublisher` на общий брокер (Redis Pub/Sub, Kafka),
   интерфейс событий менять не придётся;
3. перевести базу на PostgreSQL — профиль уже готов;
4. вынести рейтинг в Redis Sorted Set.

Узкого места в виде «раунд живёт только в памяти конкретного процесса» нет:
раунд полностью описывается строкой в БД и временем старта, поэтому любой узел
может его подобрать.

## 7. Конфигурация и горячая перезагрузка

`GameConfigService` опрашивает файл раз в секунду, сравнивая время изменения и
размер.

Почему опрос, а не `WatchService`: на bind-mount томах Docker (особенно на
Windows и macOS) файловые события до контейнера просто не доходят. Проверка
двух чисел раз в секунду надёжнее и стоит ничего.

Алгоритм применения:

```
файл изменился
  → распарсить YAML
  → GameConfigValidator.validate()
      ├─ ошибок нет → применить, опубликовать GameConfigUpdatedEvent
      └─ ошибки есть → ОСТАВИТЬ ПРЕДЫДУЩУЮ конфигурацию,
                        показать текст в GET /api/admin/config/status
```

Сломанный файл никогда не роняет игру — работает последняя корректная версия.
Новая конфигурация применяется только к **новым** раундам: у летящих свой
снимок параметров.

Админка пишет тот же файл через `GameConfigYamlWriter`, который **заново
генерирует комментарии**. Иначе первое же сохранение из UI превратило бы
документированный конфиг в безликий дамп, и один способ настройки уничтожил бы
другой. Тест `GameConfigYamlWriterTest` проверяет, что после записи в файле
по-прежнему есть и пояснения, и имена параметров из постановки
(`points_per_line`, `line_N_loot_prob`, `multiplier_tier_N_value`).

## 8. Реальное время

Основной канал — WebSocket `/ws/game?token=…`. Сервер только вещает; ни одной
игровой команды через сокет не принимается, чтобы не заводить второй,
менее проверяемый путь исполнения.

События: `round.tick`, `round.level`, `round.boost`, `round.cashout`,
`round.crash`, `round.settled`, `history.updated`, `rating.updated`,
`config.updated`.

Резерв — опрос REST. `useFlight` на клиенте раз в 700 мс запрашивает
`GET /api/rounds/{id}/state`, если сокет не открыт. Механика полностью
работоспособна и без сокета: теряется плавность подсветки, не более.
Это осознанная страховка от корпоративных прокси, вырезающих upgrade.

Устойчивость соединения: экспоненциальные переподключения
(0.5 → 1 → 2 → 4 → 8 с) и heartbeat раз в 25 секунд против таймаутов прокси.

## 9. Frontend

- **Без маршрутизатора.** Экранов шесть, переходы задаются игровым циклом, а
  не адресной строкой; бонусная игра внутри личного кабинета не нуждается в
  глубоких ссылках. Состояние — редьюсер в `GameContext`. Исключение одно:
  админка открывается по якорю `#admin`, чтобы проверяющий попадал в неё
  напрямую.
- **Без UI- и анимационных библиотек.** Canvas 2D и CSS-переменные. Это и
  требование «не использовать тяжёлые графические библиотеки», и способ
  удержать 60 FPS предсказуемо.
- **Canvas отвязан от рендера React.** `FlightCanvas` читает состояние через
  `ref` и крутит собственный `requestAnimationFrame`: перерисовки React не
  влияют на плавность полёта, и наоборот.
- **Звук синтезируется.** `AudioEngine` собирает эффекты из осцилляторов и
  шумовых буферов Web Audio API. В репозитории нет ни одного аудиофайла, а
  высота звука подъёма растёт вместе с номером уровня.
- **Темы через CSS-переменные.** Атрибут `data-theme` на корне переключает
  палитру целиком; логика о цветах ничего не знает.
- **Восстановление сессии.** Токен в `localStorage`; при загрузке страницы
  клиент спрашивает `GET /api/rounds/active` и, если раунд не закончен,
  возвращает игрока прямо в полёт.

## 10. Безопасность

| Мера | Реализация |
| --- | --- |
| Пароли | PBKDF2WithHmacSHA256, 120 000 итераций, соль на пользователя, сравнение за постоянное время |
| Сессии | серверный токен в таблице `sessions`; не JWT, потому что сессия хранит ещё и флаг показанного апсейла |
| Идентификация запроса | `Authorization: Bearer`, `X-Session-Token` или `?token=` для WebSocket |
| Авторизация раунда | каждая операция сверяет владельца раунда |
| Гонки по балансу | `@Version` на `UserAccount` |
| Утечка исхода | точка краха и уровень бустера не покидают сервер до завершения раунда |
| CORS | только для dev-портов, в Docker-стенде фронт и API на одном origin |

**Ограничения прототипа** (осознанные, перечислены в [FEATURES.md](FEATURES.md)):
нет ограничения частоты запросов, нет HTTPS внутри стенда (терминируется выше),
админ-API не разделяет роли — доступен любому авторизованному пользователю,
поскольку эксперт должен пройти сценарий 5 без отдельной учётной записи.
